# Decisions

## Решение №001

Дата: 17.06.2026

Название: нормы расхода хранятся в базе знаний.

Причина: норма расхода зависит от технологии, а не от материала.

Последствия: модуль материалов не содержит нормы расхода.

Статус: принято.

## Решение №002

Дата: 17.06.2026

Название: база материалов наполняется автоматически.

Причина: ручное наполнение не масштабируется.

Последствия: администратор выполняет роль модератора.

Статус: принято.

## Решение №003

Дата: 17.06.2026

Название: поиск дублей выполняется только внутри категорий.

Причина: у разных товарных групп разные характеристики.

Последствия: сначала определяется категория материала, затем выполняется сравнение.

Статус: принято.

## Решение №004

Дата: 17.06.2026

Название: основным техническим контуром является FastAPI API-first backend.

Причина: платформа должна развиваться как модульная data-платформа, где UI не
определяет доменную архитектуру.

Последствия: основной интерфейс разработки находится под `/api/v1`; старый
шаблонный UI не считается архитектурной основой.

Статус: принято.

## Решение №005

Дата: 17.06.2026

Название: PostgreSQL и SQLAlchemy async являются основным слоем хранения.

Причина: долгосрочная платформа требует связной реляционной модели,
транзакционности, истории изменений и масштабируемого API-доступа.

Последствия: старый SQLite/SQLModel прототип считается устаревшим и не должен
использоваться для новых модулей.

Статус: принято.

## Решение №006

Дата: 18.06.2026

Название: Модуль материалов переопределен как Material Hub.

Причина: база материалов должна быть каноническим фундаментом платформы, а не
производной от прайсов поставщиков.

Последствия: производители и retail-источники формируют канонические
материалы; поставщики подключаются позже и сопоставляют свои позиции с
существующими `Material`. Для MVP ручная загрузка ограничена CSV и XLSX.

Статус: принято.

## Решение №007

Дата: 18.06.2026

Название: старый слой `DataSource / RawProductLine / SupplierOffer` удален из рабочего контура.

Причина: старой базы нет, проект запускается с нуля, поэтому нет необходимости
сохранять обратную совместимость с прототипом загрузок и предложений.

Последствия: ручная загрузка идет через `SupplierUpload` и
`SupplierUploadRow`, спорные совпадения через `MaterialMatchCandidate`,
актуальные цены через `SupplierPrice`, история цен через `PriceHistory`.

Статус: принято.

## Решение №008

Дата: 18.06.2026

Название: реальные источники подключаются через отдельный слой интеграций.

Причина: Material Hub должен оставаться канонической доменной моделью, а
особенности сайтов не должны попадать внутрь моделей `Material`,
`CatalogProduct` или `SourceTask`.

Последствия: для каждого источника создается адаптер интеграции. Адаптер
работает через `Source`, `SourceTask`, `SourceTaskLog`, `SourceTaskResult`,
`CatalogProduct`, `MaterialMatchCandidate` и `PriceHistory`. Первый источник
Sprint 02 — Лемана ПРО.

Статус: принято.

## Решение №009

Дата: 18.06.2026

Название: Бауцентр используется как первый рабочий retail-источник вместо Лемана ПРО.

Причина: прямой server-side доступ к Лемана ПРО вернул `403 Forbidden`, а
антибот-обходы не входят в правила Sprint 02. Бауцентр предоставляет доступные
публичные страницы, `robots.txt` и `sitemap.xml`, включая товарные URL в
`/product/...`.

Последствия: Лемана ПРО остается в backlog/fallback до появления официального
feed, API, партнерской выгрузки или ручного разрешенного fixture. Для
формирования первичной retail-базы используется Бауцентр через отдельный
адаптер интеграции. `Material` остается канонической сущностью, а Бауцентр
является только одним из источников данных.

Статус: принято.

## Решение №010

Дата: 18.06.2026

Название: сайт производителя и интернет-магазин одного бренда являются разными источниками.

Причина: основной сайт производителя обычно содержит технологии, документы,
сертификаты, системы и рекомендации по применению. Интернет-магазин того же
бренда содержит ассортимент, цены, наличие и торговые карточки. Эти потоки
данных имеют разные ACTION, периодичность обновления и риски доступа.

Последствия: для Гранд Лайн, ТЕХНОНИКОЛЬ и аналогичных компаний основной сайт
создается как `MANUFACTURER` source, а интернет-магазин как отдельный `RETAIL`
source. Данные обоих источников сопоставляются с одним каноническим `Material`,
но не смешиваются на уровне `Source`.

Статус: принято.

## Решение №011

Дата: 18.06.2026

Название: Material Hub собирает все релевантные категории для частного домостроения.

Причина: цель платформы — максимально полная и актуальная база материалов,
документов, цен и наличия для частного домостроения, а не демонстрационная
выборка из нескольких карточек.

Последствия: тестовые ограничения используются только для проверки адаптера.
Боевой сбор выполняется через управляемые параметры `SourceTask`: `scan_mode`,
`max_pages`, `max_attempts`, `max_documents`, `category_url_contains`.
Полный сбор по источнику запускается явно через `scan_mode: FULL`; результаты
все равно проходят через `CatalogProduct`, `Material`, `MaterialMatchCandidate`
и модерацию качества.

Статус: принято.

## Решение №012

Дата: 18.06.2026

Название: цены собираются из публичных retail API, официальных выгрузок и прайсов поставщиков.

Причина: цены являются первоочередными данными для смет, закупок и аналитики.
HTML-страница может содержать неполные или нулевые цены, а реальные цены часто
подгружаются отдельным публичным API, feed или прайсом.

Последствия: для каждого retail-source адаптер сначала ищет официальный feed
или публичный endpoint цен. Если цена доступна через API, она сохраняется в
`CatalogProduct`, а изменения фиксируются в `PriceHistory`. Если API/feed
недоступны, используются CSV/XLSX прайсы поставщиков или ручные выгрузки.
Фиктивные цены `0` не сохраняются как реальные.

Статус: принято.

Причина:

Статус:
Принято.

19.06.2026

Дата:
19.06.2026

Название:
Строительные группы являются отдельной классификацией поверх категорий материалов.

Причина:
Категория материала отвечает на вопрос "что это за товар", а строительная

закупками и аналитикой цен.

Принято.

## Решение №017

Дата:
19.06.2026

Название:
Работа выполняется в границах выбранного модуля.

Причина:
Платформа становится модульной, и изменения в одном модуле не должны
незаметно менять соседние модули, их данные или ответственность.

Последствия:
Если работа объявлена как "работаем в Модуле 1", редактируется только Модуль 1.
Сопутствующие изменения в других модулях допускаются только после отдельного
объяснения: что меняется, зачем это нужно и какой риск снимает.

Статус:
Принято.

19.06.2026

## Решение №019

Дата:
19.06.2026

Название:
Обсуждения ведутся по нумерованной повестке.

Причина:
В рамках одной итерации часто обсуждаются архитектура, интерфейс, данные и
очередность работ. Нумерация пунктов позволяет явно согласовывать, откладывать
или возвращать отдельные вопросы без потери контекста.

Последствия:
При обсуждении нескольких вопросов помощник формирует нумерованную повестку.
Пользователь может ответить: "пункт 1 согласован", "пункт 2 на подумать",
"пункт 3 делаем". Действия выполняются только по согласованным пунктам.

Статус:
Принято.

## Решение №021

Дата:
19.06.2026

Название:
Источник разделяется на направление источника и раздел сайта.

Причина:
Категория источника и категория внутри источника похожи по названию, но решают

## Решение №022

Дата:
19.06.2026

Название:
Дубли, альтернативы и аналоги имеют разные значения.

Причина:
Для смет и закупок нельзя смешивать один и тот же материал, похожий материал и
тот же материал у другого поставщика.

Последствия:
В Material Hub используются определения:

- дубль — одна и та же каноническая позиция;
- альтернатива — тот же материал с теми же характеристиками у другого
  поставщика;
- аналог — близкий материал с похожими характеристиками, но другого бренда или
  производителя.

Проверка выполняется только внутри совместимой категории или подкатегории.

Статус:
Принято.

## Решение №023

Дата:
19.06.2026

Название:
Рейтинги поставщиков и материалов закладываются заранее.

Причина:
Будущие модули закупок, маркетплейса и личных кабинетов будут использовать
доверие к поставщику и материалу. Лучше заложить модель заранее, но не
генерировать оценки автоматически на этапе MVP.

Последствия:
Для поставщиков предусматриваются будущие критерии: общий балл, уровень цен,
скорость доставки, надежность наличия, качество документов, коммуникация,
процент успешных поставок и отзывы.

Для материалов предусматриваются будущие критерии: общий балл, качество,
удобство применения, полнота документации, повторные покупки и отзывы.

До появления пользовательских оценок рейтинги считаются отсутствующими.
Material Hub не создает рейтинги самостоятельно.

Статус:
Принято.

## Решение №024

19.06.2026

Паспорт модуля не означает, что функционал модуля уже реализован.

Статус:
Принято.

## Решение №025

Дата:
20.06.2026

Название:
Конвертер единиц работает только от подтвержденных характеристик материала.

Причина:
Для смет, сравнения цен и закупок нужно переводить штуки, листы, мешки,
бухты, килограммы, квадратные и кубические метры между собой. Но универсальная
конвертация без характеристик материала приводит к ошибочным расчетам.

Последствия:
В Material Hub добавляется UnitConversionRule.

Правило конвертации может быть привязано к Material, категории или
подкатегории. Конвертация выполняется только если у материала есть необходимые
характеристики: размеры, вес упаковки, длина бухты, вес одной штуки и другие
подтвержденные данные.

Если данных недостаточно, система не угадывает результат и отправляет материал
в список "Требует данных для конвертации".

Статус:
Принято.

## Решение №026

Дата:
20.06.2026

Название:
Material Hub v2.0 добавляет KnowledgeResource без удаления MaterialDocument.

Причина:
Текущая система уже использует MaterialDocument в API, задачах анализа,
документах материала и существующих данных. Прямое переименование или удаление
сломало бы совместимость. При этом v2.0 требует более широкой сущности:
ресурс может быть связан не только с материалом или производителем, но и с
ConstructionGroup, Category, Subcategory и MaterialType.

Последствия:
MaterialDocument сохраняется как совместимый слой текущего модуля.
KnowledgeResource становится расширенным v2.0-слоем для ссылок, метаданных,
извлеченных данных и связей ресурсов знаний.

Существующие MaterialDocument мигрируются в KnowledgeResource через поле
legacy_document_id. Внешние PDF не скачиваются и не хранятся локально.

Статус:
Принято.

## Решение №028

Дата:

## Решение №032

Дата:
15.07.2026

Название:
Module №1 — Product Logic, Canonical Material Rules, Analyzer Boundaries, Work Cost Rules and UI Structure.

Причина:
После завершения backend/service foundation Module №1 уточнена продуктовая логика модуля. Новое решение также устраняет противоречия старых формулировок, которые допускали хранение материалов без цены или смешивали анализатор, стоимость работ, виджеты и быстрые действия.

Решение:
Module №1 хранит и подготавливает данные о материалах / товарах, ценах материалов, продавцах и местах покупки, характеристиках материалов, применимом расходе, упаковке, документах, технических данных, источниках, анализаторе, нормализованном справочнике работ, стоимости работ от исполнителей, качестве и модерации данных, а также пакетах данных для других модулей.

Module №1 не рассчитывает технологии, количество материалов, объемы работ, итоговую смету, PDF/XLS и полноценную рыночную аналитику. Эти зоны остаются за профильными модулями: Module №2 отвечает за технологии и количество, Module №5 — за смету и деньги, Module №7 — за параметры объекта, Module №11 — за полноценную аналитику, Module №3 — за пользователей, роли и доступы.

Канонический материал:
Канонический материал — это уже нормализованный материал / товар, имеющий цену. Материалы и товары без цены не собираются как материалы, не создаются как `Material`, не создаются как `CatalogProduct`, не создаются как material candidate, не сохраняются в каталоге материалов, не передаются в Module №2, не передаются в Module №5, не считаются technical-only material, не считаются moderation candidate и не считаются normal business category.

Запрещено использовать формулировки: technical-only material without price, technical-only candidate without price, moderation candidate without price, material without price may be stored for later completion.

Источник без цены может быть зафиксирован только как техническая ошибка обработки или source/evidence, но не как материал. Документ, характеристика или техническое описание со страницы без цены может быть привязано только к уже существующему каноническому материалу, у которого цена есть. Такое уточнение не создает новый материал или material candidate.

Импорт и создание канонического материала:
Импорт из сайта, карточки товара, каталога, прайса или файла не создает канонический `Material` напрямую. Обязательная логическая цепочка:

```text
источник
→ сырые извлеченные данные
→ проверка наличия цены
→ нормализация
→ сопоставление / дедупликация
→ модерация или подтвержденное безопасное действие
→ канонический Material
```

Запись без цены должна быть отклонена до создания material candidate.

Цена и история цен:
Цена материала относится к конкретному наблюдению источника. Для цен должен сохраняться контекст и история: источник, продавец / поставщик, единица цены, упаковка, регион, дата наблюдения и статус. Новое ценовое наблюдение не должно безвозвратно перезаписывать предыдущую историю цен. Устаревшая цена может получить другой статус или быть архивирована, но не должна исчезать без истории.

Анализатор:
Анализатор работает только с заданным источником. Допустимые типы входа: сайт и ручной ввод из файла. Источник задается системой, администратором, настройкой источника или загруженным файлом.

Анализатор не должен самостоятельно искать сайты, гуглить поставщиков, выбирать источник, искать стоимость работ, парсить стоимость работ, собирать цены работ, создавать подрядчиков, создавать пользователей, рассчитывать количество, рассчитывать технологии или рассчитывать смету.

Анализатор извлекает из заданного источника материал / товар, цену материала, единицу цены, место покупки, поставщика / продавца, производителя, категорию, характеристики, расход если он указан, упаковку, документы, технические данные, изображения и признаки качества данных.

Документы и evidence:
Сайт, карточка товара и raw-страница являются source/evidence, но не являются document record сами по себе. Документ может быть извлечен или обнаружен на карточке товара, но карточка товара не должна автоматически классифицироваться как документ.

Стоимость работ:
Стоимость работ является отдельным разделом Module №1. Стоимость работ не ищется на сайтах, не парсится, не собирается анализатором, не является ценой материала и не является внешним price observation материала.

Единственный источник стоимости работ — исполнитель / подрядчик в будущем личном кабинете. Исполнитель выбирает работу из нормализованного справочника, не создает произвольный технический `work_code` через форму, вводит свою стоимость, указывает единицу измерения, регион, контакты и применимые комментарии. Поддерживаемые типы цены: fixed и range. Для range обязательно `price_max >= price_min`.

Module №1 хранит и валидирует стоимость работ. Module №5 позднее использует эти данные при формировании сметы. Запись исполнителя в Module №1 не должна автоматически создавать пользователя, роль или учетную запись Module №3.

Market sanity check:
Module №1 поддерживает quality/sanity signal для стоимости работ: в пределах рынка, ниже рынка, выше рынка, недостаточно данных, требует проверки. Это не полноценная рыночная аналитика. В этом решении не закрепляются конкретные числовые пороги, проценты или минимальное число наблюдений. Полная рыночная аналитика относится к Module №11.

Верхние вкладки Module №1:
Точный список верхних вкладок:

1. Обзор
2. Материалы
3. Документы и техданные
4. Стоимость работ
5. Источники и анализатор
6. Модерация и качество

Не делать отдельными верхними вкладками: Эталонные материалы, Экспортные пакеты, Лаборатория извлечения, Поставщики, Производители работ, Участники, Наблюдения цен.

Quick Actions:
Quick Actions уже реализованы и регулируются документом `docs/Modules/ATOM_USER_QUICK_ACTIONS_v1.0.md`. Запрещено переопределять Quick Actions, описывать их как обычную навигацию, заменять быстрыми переходами, создавать второй механизм Quick Actions, дублировать registry или смешивать Quick Actions и Widgets. В `docs/Decisions.md` не нужно дублировать внутренние лимиты и технические детали Quick Actions standard.

Dashboard только отображает готовую модель, не должен знать внутренние таблицы Module №1, не должен рассчитывать статусы Module №1 и не должен превращать Widget в Quick Action. Для Module №1 принят Option E: REF source packages остаются authoring/source packages, а ручной или build-time generator создаёт детерминированные immutable versioned artifacts в `src/modules/module1/runtime_reference/<artifact_set_id>/`.

Production runtime не читает `docs/Modules/module1/reference_data` и не импортирует `tools/module1_ref_projection`. Production loader читает только generated artifacts, проверяет manifest, schema version, source и artifact hashes, counts, exclusions и compatibility contract.

Существующий `MaterialKnowledgeSeedRegistry` остаётся единственным публичным runtime registry и source of truth в режиме `legacy`. Второй публичный registry запрещён. Режим `artifact_validation` разрешает только проверку artifact package и не меняет registry, global state, базу данных, business reads, API или UI.

Режим по умолчанию — `legacy`. Неизвестный режим является configuration error. В этом решении не разрешаются `dual_read`, REF read activation или REF write activation.

Generated artifacts не содержат текущее время, случайные UUID, локальные абсолютные пути, host/user names или environment-specific значения. Повторная генерация из одинаковых source packages должна давать побайтово одинаковый результат.

Review subsets исключаются из runtime-eligible artifacts: REF-2 assignments — 48, REF-3 units — 17, REF-3 packaging assignments — 51. Известные 345 packaging/REF-2 mismatches сохраняются как diagnostics и не исправляются автоматически.

REF-2 assignments сохраняются в flattened-виде. Authoring inheritance не переносится в runtime. REF required semantics не подменяют существующие 13 legacy schemas; 28 runtime-only fields сохраняются в compatibility metadata до отдельного решения.

REF-3 extended rules сохраняются только как inactive metadata и не получают runtime executor. Work-to-material mappings не создаются. Module №1 не выполняет object/work quantity calculations.

Для `liquid_waterproofing` canonical parent берётся из REF-1, второй legacy parent сохраняется только как compatibility path. Один code не клонируется в два material types, новые writes запрещены.

Канонические единицы различаются явно: `lm` означает lumen, `linear_meter` означает погонный метр. Legacy alias `lm -> linear_meter` считается ambiguous, требует контекста и не может автоматически нормализоваться или экспортироваться как `linear_meter`.

Source package `integration_allowed=false` сохраняется. Generated manifest обязан фиксировать `runtime_activation_allowed=false` и `write_activation_allowed=false`.

До любой write-активации обязателен compatibility-aware rollback release, который распознаёт все активированные идентификаторы. Pure legacy rollback после REF-only writes запрещён.

Последствия:
Разрешено создавать и валидировать inactive generated artifacts и compatibility metadata. Legacy runtime остаётся неизменным. Любая read/write activation, изменение существующих registries, схем, единиц, базы данных, Module №2, Module №5, Dashboard, Quick Actions, Widgets или UI требует отдельного решения и отдельного спринта.

Статус:
Принято.

## Решение №035

Дата:
18.07.2026

Название:
Module №1 — Diagnostic REF-1 Dual-Read Comparison without Runtime Activation.

Причина:
После создания детерминированных inactive REF artifacts требуется проверить фактическую совместимость legacy taxonomy и REF-1 до любого read- или write-подключения. Такая проверка не должна менять production behavior, публичные lookup-контракты или существующий `MaterialKnowledgeSeedRegistry`.

Решение:
Для Module №1 разрешён режим `dual_read` исключительно как приватный диагностический comparison mode. Режим по умолчанию остаётся `legacy`; `artifact_validation` сохраняет прежнее validation-only поведение.

В `dual_read` immutable artifact package сначала проходит fail-closed validation. После этого private adapter сравнивает snapshot legacy registry с taxonomy и compatibility artifacts по стабильным кодам, parent paths и доступной semantic metadata. Результат сравнения является versioned immutable diagnostics contract, но не является runtime registry, lookup provider или источником business data.

Legacy `MaterialKnowledgeSeedRegistry` остаётся единственным business source of truth. Его public methods и semantics не меняются. REF-only groups и material types не становятся доступны normalizer, matching, moderation, Material/CatalogProduct validation, Module №2, Module №5, UI или API.

Registry mutation, database writes, REF-only writes и автоматическая регистрация REF entries запрещены. Comparison result не используется normalizer, matching или moderation. `integration_allowed=false`, `runtime_activation_allowed=false` и `write_activation_allowed=false` сохраняются.

`dual_read` обязан завершаться fail-closed при невалидном manifest/package, compatibility conflict, duplicate canonical type, неожиданном legacy-only code или обнаруженной mutation. Silent fallback и переход в REF read mode запрещены.

Любая последующая REF read activation требует отдельного решения и отдельного approval. Режимы REF write остаются запрещены до compatibility-aware persistence и rollback release.

Последствия:
Разрешены только внутренние diagnostics и локальные audit outputs вне репозитория. Второй публичный registry, новый API endpoint, UI-панель, ORM/migrations и изменения business consumers не создаются.

Статус:
Принято.
