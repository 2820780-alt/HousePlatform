# Спринты Модуль 3 — финальное закрытие v1.0

**Проект:** Строительная платформа АТОМ  
**Модуль:** Модуль №3 — Пользователи и роли  
**Назначение:** финально закрыть Module №3 перед переходом к аудиту модулей, Quick Actions, Widgets и глубокой проработке Module №1.  
**Статус:** рабочий файл для Codex.  
**Главная цель:** Module №3 должен стать законченным административным интерфейсом для человека: понятным, информативным, эргономичным и без лишней технической информации.

---

## 0. Текущий контекст

По текущему состоянию уже пройдены или почти закрыты:

```text
- Обзор модуля;
- Доступы;
- История;
- виджеты Module №3 отображаются на Dashboard;
- Quick Actions проходят отдельными платформенными спринтами;
- вкладка «Пользователи» еще требует финальной доработки;
- карточка пользователя/компании не открывается корректно;
- очередь на модерацию визуально кривая;
- часть UI показывает техническую/system-информацию.
```

Этот файл закрывает именно финальную полировку Module №3.

---

## 1. Главная рамка Module №3

Module №3 — административный кабинет платформы.

Он отвечает за:

```text
- пользователей;
- аккаунты;
- роли;
- доступы к модулям;
- доступы к виджетам;
- блокировки;
- удаление аккаунтов;
- журнал административных изменений;
- модерацию компаний и поставщиков как аккаунтов платформы;
- карточки пользователей и компаний в административном контексте.
```

Module №3 не отвечает за:

```text
- материалы;
- цены;
- документы;
- нормализацию материалов;
- бизнес-логику поставщиков как строительной базы;
- создание Quick Actions за пользователя;
- Dashboard как отдельную систему;
- Widget Registry как бизнес-логику;
- Module №1 / Module №2.
```

---

## 2. Главный UX-принцип

Платформа делается для человека.

Интерфейс должен быть:

```text
- информативным;
- понятным;
- эргономичным;
- без перегруза;
- без лишней технической информации;
- с русскими пользовательскими названиями;
- в едином атомном стиле.
```

В основном UI не показывать:

```text
- UUID;
- raw ID;
- moduleCode;
- technical enum;
- raw payload;
- API route;
- business-payload;
- summary / STATUS как пользовательский текст;
- внутренние диагностические подписи.
```

Если техническая информация нужна администратору, ее можно спрятать в раскрываемый блок:

```text
Техническая информация
```

---

## 3. Уровни прохождения Codex

```text
Средний — визуальная полировка, тексты, small UI.
Высокий — UI + данные, таблицы, карточки, фильтры, состояния.
Очень высокий — маршруты, API, backend, RBAC, сохранение данных, кросс-модульные связи.
```

# Sprint M3-F1 — Исправить открытие карточки пользователя / компании

**Уровень:** Очень высокий  
**Приоритет:** критичный  
**Цель:** клик по пользователю или компании должен открывать нормальную пользовательскую карточку, а не вести на сырой API route с ошибкой.

---

## Проблема

Сейчас при клике по пользователю открывается маршрут вида:

```text
/api/v1/admin/users-roles/view/users/<user_id>
```

и появляется внутренняя ошибка.

Так быть не должно.

Пользовательский интерфейс не должен отправлять администратора напрямую на API endpoint.

---

## Что сделать

1. Найти все кликабельные ссылки в таблице «Пользователи»:

```text
- имя пользователя;
- название компании;
- название поставщика;
- строка таблицы;
- кнопки/иконки открытия карточки, если есть.
```

2. Проверить текущие маршруты:

```text
- API route;
- UI route;
- template route;
- frontend handler;
- redirect logic.
```

3. Исправить так, чтобы открывался пользовательский экран:

Вариант А:

```text
/app/users-roles/users/<id>
```

Вариант Б:

```text
drawer / modal / side panel внутри вкладки «Пользователи»
```

Выбрать тот вариант, который лучше соответствует текущей архитектуре проекта.

4. API должен оставаться API, но не должен быть видимым пользовательским маршрутом.

5. Если карточка не может быть загружена:

```text
- показать понятный error-state;
- не показывать белую страницу;
- не показывать raw traceback;
- не показывать API response как страницу.
```

---

## Что должна показывать карточка физлица

```text
- ФИО / отображаемое имя;
- тип пользователя;
- статус: активен / приглашен / заблокирован;
- email;
- телефон;
- компания, если пользователь связан с компанией;
- регион;
- дата регистрации;
- последняя активность;
- доступные модули;
- доступные виджеты;
- блокировка: да/нет;
- причина блокировки, если есть;
- дата блокировки, если есть;
- кто заблокировал, если есть;
- последние административные действия;
- кнопки: Редактировать / Заблокировать / Разблокировать / Назначить доступ.
```

---

## Что должна показывать карточка компании / поставщика

```text
- название компании;
- тип: строительная компания / поставщик / подрядчик;
- ИНН;
- КПП / ОГРН, если есть;
- контакты;
- регион;
- юридический адрес, если есть;
- назначенный менеджер, если есть;
- статус модерации;
- статус блокировки;
- сотрудники и роли;
- доступ к модулям;
- доступ к виджетам;
- ограничения;
- история активности;
- кнопки: Редактировать / Заблокировать / Разблокировать / Назначить доступ / Модерация.
```

---

## Что скрыть из основного вида

```text
- длинные UUID;
- internal user ID;
- internal company ID;
- technical enum вроде CONSTRUCTION_COMPANY;
- moduleCode;
- raw payload;
- API path.
```

Если нужно — поместить в раскрываемый блок:

```text
Техническая информация
```

---

## Что нельзя делать

```text
- не менять всю вкладку «Пользователи» целиком;
- не менять авторизацию;
- не менять Module №1 / Module №2;
- не менять Dashboard;
- не менять Quick Actions;
- не выводить raw API response пользователю;
- не показывать техническую ошибку как страницу.
```

---

## Проверка

```text
- клик по пользователю открывает карточку;
- клик по компании открывает карточку компании;
- карточка не открывается через /api/... как пользовательский URL;
- если данных нет, есть понятный empty/error-state;
- кнопки действий видны и не ломают страницу;
- технические ID скрыты из основного вида.
```

# Sprint M3-F2 — Очеловечить таблицу «Пользователи»

**Уровень:** Высокий  
**Приоритет:** высокий  
**Цель:** таблица пользователей должна показывать понятную административную информацию, а не системные поля.

---

## Текущие проблемы

В таблице сейчас встречаются технические и перегружающие строки:

```text
user · ID: ...
company · ID: ...
CONSTRUCTION_COMPANY
не связан с компанией
закрыто: компания заблокирована
следует доступу компании к модулям
```

Это нужно заменить на понятные пользовательские формулировки.

---

## Целевой смысл таблицы

Таблица должна быстро отвечать на вопросы администратора:

```text
- кто это;
- какой тип пользователя/организации;
- активен или заблокирован;
- к какой компании относится;
- какие модули доступны;
- какие виджеты доступны;
- есть ли блокировка;
- когда был активен;
- что можно сделать.
```

---

## Целевые колонки

```text
Тип
Наименование / ФИО
Компания / Организация
Контакты
Статус
Модули
Виджеты
Блокировка
Последняя активность
```

---

## Правила отображения

### ID и UUID

Не показывать в основном UI:

```text
user · ID: ...
company · ID: ...
```

Если нужно, показывать короткую техническую информацию только в карточке пользователя в раскрытом блоке.

---

### Типы

Заменить technical enum на русский текст:

```text
CONSTRUCTION_COMPANY → Строительная компания
SUPPLIER → Поставщик
CUSTOMER → Заказчик
SPECIALIST → Специалист
USER → Пользователь
COMPANY_LEAD → Руководитель компании
```

Использовать существующие enum проекта, но отображать русские названия.

---

### Компания

```text
не связан с компанией → Без компании
— → Без компании
```

Если компания есть — показывать название, не технический ID.

---

### Модули

Заменить длинные технические фразы:

```text
закрыто: компания заблокирована → Доступ закрыт
открыто в пределах платформы → Доступ открыт
следует доступу компании к модулям → По доступу компании
```

Если показывается количество:

```text
4 модуля
3 модуля
0 модулей
```

Если доступ закрыт:

```text
Доступ закрыт
```

---

### Виджеты

```text
1 виджет
0 виджетов
закрыто вместе с компанией → Доступ закрыт
следует доступу компании к модулям → По доступу компании
```

---

### Статусы

Единые статусы:

```text
Активен
Заблокирован
Приглашен
На модерации
Отклонен
Отложен
```

Цвета:

```text
Активен — зеленый
Заблокирован — красный/розовый
Приглашен — синий
На модерации — янтарный
Отложен — серый/желтый
```

---

## Фильтры

Проверить, что фильтры работают по человеческим значениям:

```text
- тип;
- статус;
- блокировка;
- сортировка по типу;
- сортировка по имени;
- поиск по ФИО / компании / email / телефону / ИНН.
```

---

## Что нельзя делать

```text
- не удалять важные данные;
- не ломать фильтры;
- не ломать пагинацию;
- не менять источники данных шире необходимости;
- не показывать technical enum вместо русского текста;
- не перегружать таблицу дополнительными колонками.
```

---

## Проверка

```text
- таблица не показывает raw UUID;
- technical enum заменены на русский текст;
- компании отображаются человеческими названиями;
- статусы единые и понятные;
- фильтры работают;
- пагинация работает;
- клик по имени открывает карточку.
```

# Sprint M3-F3 — Исправить очередь на модерацию

**Уровень:** Средний → Высокий  
**Приоритет:** высокий  
**Цель:** блок «Очередь на модерацию» должен быть компактным, читаемым и не ломать сетку обзора.

---

## Текущие проблемы

На обзоре блок выглядит криво:

```text
- карточка заявки растянута;
- много пустоты между иконкой и текстом;
- данные разъезжаются;
- кнопки действий выглядят как длинные полосы;
- композиция не похожа на аккуратную очередь;
- блок плохо читается при изменении масштаба.
```

---

## Целевой вид

```text
Очередь на модерацию      1

[иконка] ООО «БетонПоставка Кубань»
        Поставщик
        ИНН 2322222222

[Принять] [Отклонить] [Отложить]
```

---

## Что сделать

1. Заголовок:

```text
Очередь на модерацию
```

Справа маленький бейдж количества заявок.

2. Карточка заявки:

```text
- иконка слева;
- название компании/поставщика рядом;
- тип ниже;
- ИНН ниже;
- без большого пустого пространства;
- компактная высота.
```

3. Кнопки:

```text
Принять
Отклонить
Отложить
```

Требования:

```text
- компактные;
- одинаковая высота;
- не растянуты на всю ширину;
- стоят в одну строку;
- имеют понятные цвета.
```

4. Скрытый вертикальный скролл:

```text
- если заявок много, прокручивается внутренний список;
- внешняя карточка не растягивает весь обзор;
- скролл может быть скрытым/тонким;
- прокрутка должна работать мышью и тачпадом.
```

5. Empty-state:

```text
Нет заявок на модерацию
```

---

## Что нельзя делать

```text
- не удалять очередь на модерацию;
- не удалять кнопки Принять / Отклонить / Отложить;
- не менять бизнес-логику модерации;
- не превращать очередь в отдельную страницу;
- не растягивать блок на всю высоту экрана;
- не добавлять проверку дублей, если механизма нет.
```

---

## Проверка

```text
- одна заявка отображается компактно;
- несколько заявок прокручиваются внутри блока;
- кнопки не растянуты;
- блок не ломает ряд с карточками «Модули в системе» и «Виджеты в системе»;
- empty-state работает;
- действия работают как раньше.
```

# Sprint M3-F4 — Полировка матрицы доступов и чекбоксов

**Уровень:** Средний → Высокий  
**Приоритет:** средний  
**Цель:** матрица доступов должна выглядеть спокойной и понятной. Активные чекбоксы не должны выглядеть как большие яркие кресты.

---

## Текущая проблема

Включенные чекбоксы выглядят как яркий X.

Это может восприниматься как ошибка, запрет или конфликт, хотя означает включение доступа.

---

## Целевой вид чекбоксов

```text
- размер 14–16 px;
- активное состояние — аккуратная галочка;
- неактивное состояние — тонкий контур;
- disabled — приглушенный контур/opacity;
- hover мягкий;
- без большого яркого X.
```

---

## Что сделать

1. Проверить текущий компонент чекбокса в матрице.

2. Сделать единый стиль для:

```text
- enabled checked;
- enabled unchecked;
- disabled checked;
- disabled unchecked;
- hover;
- focus.
```

3. Проверить, что логика не изменилась:

```text
если модуль закрыт → виджеты disabled
если модуль открыт → виджеты управляются отдельно
```

4. В ячейках не должно быть лишнего текста:

```text
разрешен
запрещен
зависит от модуля
```

---

## Что нельзя делать

```text
- не менять RBAC backend;
- не менять массовое назначение доступа;
- не менять registry;
- не ломать сохранение/сброс;
- не делать чекбоксы слишком яркими;
- не использовать X как активное состояние.
```

---

## Проверка

```text
- активный чекбокс выглядит как галочка;
- disabled-состояния понятны;
- виджеты отключенного модуля disabled;
- массовое назначение работает;
- сохранить/сбросить работает;
- матрица остается читаемой.
```

# Sprint M3-F6 — Финальный QA Module №3

**Уровень:** Высокий  
**Приоритет:** финальный  
**Цель:** перед закрытием Module №3 проверить все основные сценарии и зафиксировать, что модуль готов.

---

## Проверить вкладку «Обзор модуля»

```text
- счетчики компаний/поставщиков/заказчиков/специалистов;
- карточки «Модули в системе» и «Виджеты в системе»;
- очередь на модерацию;
- история изменений;
- отсутствие технического мусора;
- адаптив при масштабе 50%, 80%, 100%.
```

# Рекомендуемый порядок прохождения

```text
1. M3-F1 — отдельно, Очень высокий.
2. M3-F2 — отдельно или вместе с F5, Высокий.
3. M3-F3 — отдельно, Средний → Высокий.
4. M3-F4 — отдельно, Средний → Высокий.
5. M3-F5 — можно вместе с F2 или перед финальным QA, Средний.
6. M3-F6 — отдельно, Высокий.
```

---

# Что можно объединить

Можно объединять:

```text
M3-F2 + M3-F5
```

если Codex аккуратно работает с текстами и таблицей.

Можно объединять:

```text
M3-F3 + M3-F4
```

только если нужно быстро закрыть визуальную полировку и нет риска залезть в backend.

---

# Что не объединять

Не объединять:

```text
M3-F1 + что-либо еще
M3-F6 + любые изменения
карточку пользователя + RBAC изменения
очередь на модерацию + виджеты Dashboard
```

# Короткий промт для Codex

```text
Работаем строго в Module №3 — Пользователи и роли.

Цель: финально закрыть модуль как административный интерфейс для человека.

Главные дефекты:
1. Карточка пользователя/компании не открывается и ведет на /api/... с ошибкой.
2. Таблица пользователей показывает слишком много технической информации.
3. Очередь на модерацию визуально кривая.
4. Чекбоксы матрицы доступов выглядят как яркие X.
5. В истории и подсказках есть технические слова вроде business-payload.
6. Нужно провести финальный QA Module №3.

Не трогать:
- Dashboard, кроме проверки виджетов Module №3;
- Quick Actions;
- Module №1;
- Module №2;
- Module Registry;
- backend RBAC без необходимости.

Пользовательский UI должен быть информативным, эргономичным и без перегруза.
Технические ID, UUID, enum и API routes не показывать в основном интерфейсе.
```
